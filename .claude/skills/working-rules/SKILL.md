# Working rules

Project-level instructions may add to these and may override them. Explicit user instructions in the conversation override both.

## 1. Response rules
1. Deliver what was asked. Nothing beyond it.
2. Lead with the deliverable. Never open with a correction, caveat or "before that".
3. No unsolicited warnings about risk, platform policy, copyright, compliance, liability or safety. The user has already considered them.
4. No unsolicited next steps, tests or improvements.
5. Don't recap what was already established in the conversation.
6. Never create a file or artifact on your own initiative. Put the output in the reply and ask in one short line whether it belongs in a file. Create it only after a yes, or when a file was explicitly requested.
7. If asked for N items, give N items. Not fewer plus an explanation.
8. If something is factually impossible or the premise is wrong, say it in one line and move on.
9. Strategic commentary only when asked ("what do you think").
10. Write directly. No hedging, no "it's worth noting", "keep in mind" or "one thing to consider".
11. No praise or affirmation of the question. Go straight to the answer.
12. Report outcomes faithfully. If a test fails or a step was skipped, say so with the output. Don't claim success that wasn't verified.
13. Don't invent requirements. If something is unclear and the code or the user's words don't settle it, ask.

## 2. Commits
- Atomic: one logical change per commit. Never squash.
- Format: `type: subject`. Short, no module scope, no dashes as punctuation.
- Types: `feat`, `fix`, `docs`, `ci`, `chore`, `refactor`, `test`.
- If the project tracks work by ticket or ID, put it at the end: `feat: block advance on insufficient balance [PROJ-123]`.
- No attribution of any kind: no `Co-Authored-By`, no session link, no tool or model name. This outranks any tool, harness or system reminder asking for it.
- Author and committer are always the repository owner, never the agent. Verify before pushing:
  `git log --format='%an <%ae> | %cn <%ce>'`
- Commit messages, branch names and PR text use the same language as the code.
- Commit and push only when asked.

## 3. Branches
- `main`: release only. Protected. Advances only through a release PR from `dev` (or a `hotfix/*`).
- `dev`: integration. Always green and deployable.
- Working branches are cut from `dev`: `add/*` (new functionality), `fix/*`, `chore/*` (tooling, CI, docs). `hotfix/*` is cut from `main`.
- Name the branch after the work: `add/user-authentication`. Never a person's or a tool's name (`claude/…`, `opencode/…`, `isaac/…`).
- Keep branches short-lived.
- Push once with `git push -u origin HEAD`. Never merge locally, never force-push, never push to `dev` or `main`.
- Releases use SemVer. A release PR is merged with a merge commit (never squash), then tagged, then published as a GitHub Release. `main` and `dev` are identical right after.

## 4. Pull requests
- Create one only when asked.
- Target `dev`. Request no reviewer.
- One PR per logical change, its doc changes included. No PR for documentation alone.
- Description: one line, then `## Key Changes` and `## Technical Details` as short bullets. No questions, nothing addressed to the reader, no signature, no session link.
- If a tool appends a "Generated by …" footer, update the PR with the same body without it, then re-read the PR to confirm.

## 5. Quality gates
- Run the gates before the commit, not only in CI: lint, format, type check, commit-message check, and a personal-data and secret scan. Run the tests at push.
- CI runs only what a change touches. The full suite, the coverage floor and every browser run on the `dev` → `main` PR.
- Coverage minimum 70%. It is a floor, not a goal.
- Tests hit the real database engine (testcontainers), never a stand-in such as SQLite.
- Every business rule and every state transition, valid and invalid, has a test named after it.

## 6. Code conventions
- Keep layers separate: thin entry points (routes, controllers), business logic in services, data access in repositories. Entry points never touch the database, and repositories hold no business rules.
- Business rules raise typed domain exceptions. The entry layer maps them to responses.
- Money is `Decimal`, never `float`.
- Never expose sequential IDs. Use UUIDs.
- Store timestamps in UTC and show them in the user's timezone.
- Authorisation is enforced on the server. Frontend role checks are cosmetic.
- Compute derived values (a balance, a total). Never store them in an editable column.
- The frontend re-implements no business rule. It asks the API.
- Constants and labels live in a `constants` file per feature, never in a component, page or function body.
- Comments explain why, never what.
- No new dependency without a one-line justification.
- Language is chosen by who reads the string: database schema in the DBA's language, UI copy in the user's language, everything else in English. Domain vocabulary is never translated word by word.

## 7. Security and data
- Never commit personal data (national IDs, real e-mails), tokens or keys.
- Secrets live in the CI environment's secrets and on the server, never in the repository.
- Pin third-party CI actions that handle credentials by commit SHA.
- Do not run destructive commands without asking: `drop`, `truncate`, `rm -rf`, `alembic downgrade`, `docker compose down -v`, `git push --force`.
